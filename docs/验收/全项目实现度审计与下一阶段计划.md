> 审计类型：静态实现审查 + 既有测试证据复核；本轮未修改业务代码、数据库结构或依赖。

## 1. 执行摘要

项目已经有较完整的本地业务骨架：五个一级 Tab、Room v8 显式迁移、鱼只/鱼缸/成长/喂食/水质/换水/养护/统计页面、本地照片、校验型备份恢复和任务提醒调度均有源码。多条 Repository 和计算用例也已编写。

当前不能判定为可发布或全流程验收通过。主要阻塞是：

1. **P0 数据风险处置**：历史专项报告记载 UTP 曾卸载正式包，旧私有数据库和照片是否保留无法确认。该风险针对报告所述设备/事件；本次没有检查用户设备私有数据库内容。
2. **P1 恢复闭环缺陷**：已归档鱼只可以在列表中找到，但详情菜单没有恢复入口，Repository 又拒绝对归档状态调用通用状态变更，因此无法从 UI 恢复。
3. **P1 验收证据不闭环**：导航仪器测试源码存在但历史执行有失败/未执行；提醒真实投递、重启恢复和多个关键 UI 流程没有可靠端到端证据。
4. **P1 文档失效链接**：根 README 仍链接到已删除的 `docs/验收/导航验收矩阵.md`。
5. **本轮验证受环境阻塞**：ADB 仅发现一台真机；基于正式包卸载风险，本轮不在真机运行 connected 测试。Gradle Wrapper 本地无 8.14.4 发行版，联网下载被权限拒绝，所以本轮 Gradle 构建、单测、Lint 均未执行。

建议开发顺序：先核查正式数据并加固恢复/验收隔离，再闭环归档恢复和提醒/导航验证，然后补齐业务与 UI 验收，最后整理发布条件。

## 3. 发现与证据

### P0 — DS-01 正式应用数据完整性存在未关闭风险

- **状态**：已确认的历史测试基础设施风险；当前设备数据状态未知。
- **证据**：`docs/产品设计/第一阶段专项回归验收报告.md` 的 B-08、“正式用户数据”及“剩余风险”段落记载：默认 `com.guanyji.app` 的 connected 任务曾在 UTP cleanup 执行卸载，之后重装 APK，但无法证明原私有数据库/照片幸存。`app/build.gradle.kts` 支持 `-PacceptanceApplicationId=com.guanyji.app.qa` 隔离验收包。`LocalBackupManager.restore` 在替换前尝试建立安全副本。
- **当前实现**：Room 使用应用私有数据库，照片保存在应用文件区；备份恢复支持先检查、覆盖确认、校验和恢复失败回滚。测试可通过 Gradle property 使用 QA applicationId。
- **复现/核查**：在当事设备检查 `pm path com.guanyji.app`、应用内鱼缸/鱼只计数、照片引用和用户已有备份；仅 APK 安装成功不能证明旧私有数据仍在。该审计不访问用户数据，因此不能确认事故是否实际导致数据丢失。
- **预期/实际**：预期正式用户数据可读且有可验证备份；历史报告只能证明包曾被卸载，实际私有数据留存未知。
- **影响**：若用户数据曾被卸载清除，可能无法从当前安装恢复；这是当前最高优先级的数据风险。
- **测试覆盖/结果**：隔离数据库备份恢复和照片往返测试在历史 QA 报告中通过；它们不能验证正式用户数据。默认包 UTP 风险有历史日志证据。
- **最小方案**：先让维护者在受影响设备核对可用备份和正式数据；以后所有 connected 测试固定使用 QA applicationId，并加任务/脚本护栏阻止默认包测试。不要用审计/测试过程试探正式数据。
- **量化验收**：正式包数据/照片引用核对结果留档；备份导出后在隔离 QA 数据库恢复并逐表/照片校验；自动化任务断言 applicationId 必须以 `.qa` 结尾；确认 connected 测试日志中不出现正式包卸载。

### P1 — NAV-02 已归档鱼只没有恢复路径（已确认缺陷）

- **证据**：`app/src/main/java/com/guanyji/app/feature/fish/FishScreens.kt` 的鱼只状态筛选包含 `FishStatus.archived`，详情更多菜单在约 520-540 行只对 `fish.status != archived` 显示“归档鱼只”，管理状态选项仅对 active/quarantine 显示；没有 archived 专属恢复项。`app/src/main/java/com/guanyji/app/data/repository/LocalRepository.kt` 的 `changeFishStatus` 明确 `require(fish.status != FishStatus.archived)`，而 `archiveFish` 只做单向归档。
- **当前实现**：鱼只可归档、筛选和查看；鱼缸列表可筛选已归档缸，但仓库/API/UI 未见鱼缸恢复函数或按钮。
- **复现步骤**：对一条在养鱼执行“归档鱼只”，返回列表选“归档”，打开详情。尝试现有状态流程将其改回在养；对于鱼缸，归档后在已归档筛选中打开详情。
- **预期/实际**：产品设计原则“归档优先于永久删除”要求历史保留且可恢复；实际鱼只详情没有恢复入口且 Repository 拒绝通用改状态。鱼缸同样没有恢复操作，属于并列流程缺口。
- **影响**：误归档后用户无法通过产品界面恢复在养状态；已归档鱼缸无法重新启用。
- **测试覆盖/结果**：`LocalRepositoryTest.archiveSynchronizesEligibleFishKeepsOtherStatusesAndHistoryAndDisablesFutureCare` 等覆盖归档副作用，但未覆盖恢复；历史测试仅数据层运行过归档，恢复无证据。本轮未执行。
- **最小方案**：增加显式 `restoreFish`/`restoreTank` 操作与确认/校验规则；恢复鱼只前要求目标缸 active，恢复鱼缸不得自动恢复已归档鱼只或旧任务，明确由用户单独处理；成功后同步调度。
- **量化验收**：鱼和缸均可从归档列表恢复；恢复前后档案 ID、历史记录和照片引用不变；已归档目标拒绝恢复鱼只；恢复不自动复活旧任务；重复点击安全；对应 Repository 仪器用例通过。

### P1 — CARE-01 提醒触发与重启恢复仅有代码、没有端到端验证

- **测试覆盖/结果**：Repository 的拒权和重复任务用例在历史 QA 报告通过；真实 AlarmManager 投递、receiver 重启路径未通过设备验证。本轮设备测试因正式数据安全约束未运行。

- **量化验收**：API 26、32、33+ 至少各验证适配路径；许可拒绝时任务状态仍可查询；允许时每个 task ID 只产生一个有效提醒；开机/时区/时间变更后待办数量与提醒数量一致；冷/热启动点击均进入对应 task，过期/取消任务不展示陈旧通知。

### P1 — DATA-02 备份恢复具备保护流程，但正式库故障矩阵没有完整证据

- **状态**：部分实现/部分验证。
- **证据**：`app/src/main/java/com/guanyji/app/data/backup/LocalBackupManager.kt` 的 `export` checkpoint WAL、打包数据库和照片哈希；`inspect`/`restore` 走 `extractAndValidate`；恢复前建立安全副本、替换 DB/照片、验证 live photo references，失败时尝试回滚。`LocalBackupManagerTest` 覆盖隔离库往返、照片引用、损坏 checksum/缺失照片、未来格式/重复条目。`DatabaseFactory` 注册 v1-v8 migration，无 destructive fallback；`LocalRepositoryTest` 有迁移链与失败回滚用例。专项报告称测试隔离库备份用例通过，但迁移后续照片问题曾有一项待复测记载，且正式数据不可确认。
- **复现步骤**：在 QA 包建立鱼缸、鱼、所有类型记录与照片，导出；分别构造损坏 manifest、错误哈希、缺失照片、低磁盘空间和恢复中进程中断包，再 inspect/restore 并重启检查。
- **预期/实际**：预期坏包在替换数据前拒绝，恢复中断可回滚到旧 DB 与照片，成功恢复后引用全可解析。源码设计了安全副本和校验；低空间/文件系统替换失败/进程中断后正式恢复全链尚无完整运行证据。
- **影响**：低概率设备文件操作失败可能导致恢复失败或回滚不完整，影响用户全部本地数据。
- **测试覆盖/结果**：若干隔离库 instrumentation 在历史报告通过；故障注入矩阵未覆盖。本轮 Gradle 被 Wrapper 下载阻塞，未复跑。
- **最小方案**：补充可注入文件操作/磁盘空间的恢复状态机测试；在随机 DB 名、临时照片根和 QA 包运行正式恢复流程；恢复后逐表计数、外键、哈希和照片字节校验。
- **量化验收**：成功包恢复后所有实体行数/关联与 manifest 一致、所有照片 SHA-256 一致；至少 5 类损坏/中断场景都证明旧数据仍可读取；恢复临时 Room 连接均关闭；无 destructive migration；迁移 v1-v8 在干净 CI/模拟器完成。

### P1 — FISH-01 归档鱼只恢复缺失，且列表和详情状态异常仍存在验证盲区

- **状态**：部分实现；恢复缺失已作为 NAV-02；列表错误状态为已实现不足/未验证。
- **证据**：`FishScreens.kt` 实现名称/鱼种搜索、鱼缸与状态过滤、最近添加/入缸日期/最近测量排序，使用 `rememberSaveable` 保存控制项；`FishViewModel` 的详情流有 Loading/Success/NotFound/Error，但列表 `fish` 与 `tanks` StateFlow 以 `null` 初值且未捕获错误；`FishLoadStateTest` 测详情状态，缺少列表流错误 UI 测试。`LocalRepository` 有初始成长记录事务、状态事件、转缸事件与待办取消；对应多条仪器测试源码存在。
- **复现步骤**：在多条真实测试鱼上执行查询、状态/鱼缸过滤、排序；旋转/重建/杀进程后检查；使列表 DAO Flow 抛错；归档后尝试恢复。
- **预期/实际**：筛选和排序功能在源码中存在，不判为缺失；配置项用 rememberSaveable，但滚动位置没有明确 saveable 策略。列表 DAO 异常没有明确 Error UI 状态，可能表现为空/崩溃而非可恢复错误。恢复问题见 NAV-02。
